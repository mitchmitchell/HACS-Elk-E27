## Before you upgrade

**Upgrading from v0.1.7:** delete the Elk E27 Alarm Engine Integration entry, upgrade
through HACS, then **add the integration again**. Do not rely on an in-place upgrade alone.

Entity unique IDs and device identifiers follow the panel **MAC address** when the panel
reports one, otherwise the panel **hardware serial**, otherwise the **config entry ID**.

**Panels today report neither MAC nor hardware serial.** For those panels the config entry
**unique_id stays unset**, setup dedupes on **host:port**, and devices and entities are keyed
on the **config entry ID**. If the panel IP changes, delete the entry and add it again at the
new address (re-link alone is not enough).

After re-adding the entry, update any automations, scripts, and dashboards that reference the
old entity or device IDs.

1. **Settings → Devices & services → Elk E27 Alarm Engine Integration → ⋮ → Delete**
2. Upgrade to v0.1.8 in HACS and restart Home Assistant
3. **Add integration** and complete setup
4. Re-point automations, scripts, and dashboards at the new entities

## What's Changed

### Arm automatic: no duplicate arm when two calls for the same area overlap (#49, fixes #43)

- Before: if a second `elke27.alarm_arm_automatic` call for an area was waiting behind a
  first call, it could send a second arm. The panel's status could still read disarmed after
  the first call had armed.
- Now only a call that is **queued behind another call on the same area** polls `area_get_status`
  for up to 2.5 s. It skips bypass, arm and rollback only when a **fresh** reply shows the
  area fully armed or in exit-delay arming (see #54 below).
- There is no remembered-arm marker. A call made after the first one has finished does one
  live status read and arms normally unless that read shows armed or exit-delay arming.
- Why it matters: a redundant arm is usually harmless. But if the panel refused it, the
  second call could undo bypasses the armed area depends on.
- Unchanged: disarm still wins over automatic arming in progress, rollback happens only on a
  definitive refusal, and panel refusals are never retried.

### Batch B: setup errors, re-linking and validation (#48, merged 2e589767)

- **Setup errors:**
  - Bad credentials or an invalid link at setup now stop setup and show a **re-link
    (reauthentication) prompt**.
  - Temporary problems (connection, timeout, panel errors during the first refresh) now
    **retry setup** automatically.
- **More places start the re-link prompt.** The integration asks you to re-link (once per
  load) when the panel rejects the link or credentials:
  - while reconnecting;
  - during the refresh after a reconnect or a later status refresh;
  - when you arm, disarm, bypass a zone or run another command.
- **Re-link flow:**
  - It uses Home Assistant's standard reauthentication step.
  - It keeps the stored host and port.
  - It refuses a different panel ("wrong panel"). It matches the panel by its MAC address or
    hardware serial.
  - Wrong credentials now show *invalid authentication* instead of *cannot connect*.
- **Panel identity:** new entries store the panel's MAC address in Home Assistant's standard
  format (lower case with colons) when the panel reports one.
- **Codes:** non-numeric codes are rejected with a clear validation error, both on the alarm
  panel and in `elke27.alarm_arm_automatic` / `elke27.zone_bypass`.
- **Reliability:**
  - Full and per-device refreshes no longer overlap.
  - A dropped connection stops a refresh cleanly, and the refresh on reconnect runs once.
  - Narrower error handling, so cancellations aren't swallowed.
- Setup screens: labels and errors moved to translations.

### Reconnect policy (#53, merged bac4c1ac)

- After a disconnect, the **reconnect loop keeps retrying** transport, protocol and unknown
  errors with **exponential backoff and jitter** (base delay grows from 2 s, capped at about
  **300 s** before jitter, so sleeps can reach roughly **360 s**).
- **Auth refusals** (rejected link keys or credentials) **stop reconnecting** and start the
  standard **re-link (reauthentication) flow once** instead of retrying forever.
- After **three non-transport reconnect failures since the last successful connect** (transport
  failures in between do **not** reset the count), Home Assistant **Repairs** shows a
  **`reconnect_failed`** issue for that entry. It clears on the next successful connect, on
  integration unload, or when the config entry is removed.
- **Logging:** **WARNING once per streak** for non-transport failures (with traceback for
  unexpected errors on that first failure); further non-transport failures log at **DEBUG**
  until the next successful connect. Transport failures log at **DEBUG** only.
- Entities stay unavailable while disconnected; the loop does not give up except on auth
  refusal or unload.

### Exit delay: ARMING state and automatic arm skip (#54) <!-- pending merge -->

- **Alarm control panel entity:** shows **ARMING** while the area is in the panel exit delay
  (requires `elke27` **0.3.12** with exit-delay fields on area state).
- **`elke27.alarm_arm_automatic`:** both the contended poll (#49) and the uncontended live
  `area_get_status` read skip bypass, arm and rollback only when the fresh reply shows the
  area fully armed **or** exit-delay arming. Missing or unknown fields never skip.
- Why it matters: during exit delay the panel is not fully armed yet, but a second automatic
  arm should not run or roll back bypasses the first arm depends on.

### Breaking changes and what to do

See **Before you upgrade** above if you are coming from v0.1.7.

1. **Entity unique IDs and device identifiers may change when you re-add the integration
   (#48).**
   - What happens: identity uses panel MAC, then panel hardware serial, then the config entry
     ID. When the panel reports neither MAC nor serial (typical today), the config entry
     **unique_id is unset**, dedupe uses **host:port**, and devices and entities use the
     **config entry ID**. Re-adding after delete creates entities under these rules.
   - What to do: follow the **Before you upgrade** steps, then fix automations, scripts, and
     dashboards that still reference old entity or device IDs. If only the panel IP changed,
     delete and re-add at the new address.
2. **Non-numeric `code` is rejected by `elke27.alarm_arm_automatic` and `elke27.zone_bypass`
   (#48).**
   - What happens: the call fails validation before anything is sent to the panel.
   - What to do:
     1. Open each automation or script that calls these actions.
     2. Make sure `code` is digits only (for example `"1234"` or `!secret elk_alarm_code`, where
        the secret is digits only).
     3. Run each one once and check the trace.
3. **Re-link step renamed** (`relink` → `reauth_confirm`) (#48).
   - What happens: only a re-link prompt that's open during the upgrade is affected.
   - What to do:
     1. Dismiss any open re-link prompt.
     2. Reload the integration (**Settings → Devices & services → Elk E27 Alarm Engine
        Integration → ⋮ → Reload**).
     3. Open the new prompt if one appears.
4. **Setup and runtime auth failures behave differently (#48).**
   - Bad credentials or an invalid link now show a setup error plus a re-link prompt (before:
     endless retry or a raw error).
   - Library errors during the first refresh now retry setup (before: a setup error).
   - A rejected link while running now also raises a re-link prompt.
   - What to do:
     1. If a re-link prompt appears, open it and enter the access code and passphrase from
        your installer.
     2. If the integration shows "retrying setup", check that the panel is powered and
        reachable. It connects by itself once it is.
5. **Re-link checks that it's the same panel (#48).**
   - What happens: re-linking aborts with "wrong panel" if the panel's MAC address or
     hardware serial doesn't match the entry.
   - What to do:
     1. Check that the host points at the same panel.
     2. If you really replaced the panel, delete the entry and add it again. Entity IDs then
        change.
6. **Automatic reconnect auth and Repairs (#53).**
   - What happens: rejected credentials or link keys during automatic reconnect stop retrying
     and start re-link once; entities stay unavailable until re-link completes or you reload.
     Three non-transport reconnect failures **since the last successful connect** (transport
     failures in between do not reset the count) raise a **`reconnect_failed`** Repairs issue;
     reconnect still retries with backoff until the link returns or the entry unloads.
   - What to do: complete re-link when prompted; for a persistent Repairs issue, check panel
     reachability and logs, or reload/remove the entry if the panel was replaced.
